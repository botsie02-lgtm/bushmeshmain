# Security v2 ↔ Android production-security: implementation-level compatibility review

**Review date:** 2026-11-10. **Security v2 reviewed:** `feature/security-v2-group-transactions-v1` at `8eeb659dfb2156c676cf1b69d407edb644cdcff8`. **Android reviewed:** `feature/android-production-security-v1` at EXACT `b0558b643ffed8e839267bca16d4ae5cd363536b`. Both derive from the requested Wave 3 baseline. This document is **a cross-branch specification**, NOT an integration, native patch, approved API, or production activation.

**Decision: INCOMPATIBLE. Do not adapt AndroidSecurityEpochStorage by structural cast. Security v2 and v3 live activation remain DISABLED.** No frozen Security v1/Protocol v1 changes are necessary merely to document the gaps.

## Source-inspection evidence

Reviewed Android:
- `src/security/platform/androidProductionSecurity.ts`: `AndroidSecurityNativeBridge` provides `commitEpoch(...): Promise<boolean>`, `epochHigh(...): Promise<number>`; `AndroidSecurityEpochStorage.commitGroupEpoch({transactionId,groupId,commitDigest,expectedEpoch,nextRecord:GroupRecord,keyRef,newEpochKey})` and `getHighWatermark()`. `AndroidSecureSecretStore` and `AndroidSecurityMetadataStore` implement **Security v1 ports**, not V2.
- `android/app/src/main/java/com/bushmeshmain/security/BushMeshSecurityCore.kt`: local SQLite `entries`, `nonce`, `replay`, `consumed`, `epoch_high`, `epoch_commit`, `PRAGMA synchronous=FULL`, application-class lock, transactions, AES-GCM/Keystore wrapping, and `commitEpoch`. The old key reference remains stored; no V2 journal/roster validation/recipient receipts exist.
- `BushMeshSecurityModule.kt`: only native `commitEpoch` and `epochHigh` bridge methods, general error mapping to `SECURITY_UNAVAILABLE` / `INVALID_INPUT` / `KEY_NOT_FOUND`; no exact V2 conflict/rollback recovery codes.
- `android/app/src/androidTest/.../BushMeshSecurityInstrumentationTest.kt`: verifies V1 storage restart, nonce/replay, epoch CAS/idempotency and SQLite interrupted *meta write*. **Instrumentation requires a device**; CI compilation and a JVM test are not evidence of actual Android Keystore Curve25519 support or V2 power-cut recovery.
- `docs/ANDROID_PRODUCTION_SECURITY_V1.md`: explicitly describes hardware anti-rollback as unsupported/unverified; reports Galaxy S22+ *not yet validated* at reviewed SHA. Keys in a V1 `GroupRecord` must not be treated as signed V2 roster evidence.
- `src/security/v2/contracts.ts`, `GroupTransactionsV2.ts`, `testing/InMemorySecurityV2TransactionStore.ts`, `src/convoy/enrolmentV3/SECURITY_V2_CONTRACT_PROPOSAL.md`, `docs/WAVE3_SECURITY_V2_FORMAL_REVIEW.md` and `src/bushmesh/protocol/securityBoundary.ts`.

## Substantial semantic mismatches

1. **Record shape and authorization**: Kotlin `commitEpoch` only checks `groupId` and `currentEpoch` in its JSON argument; it never verifies current owner/admin chain, `SignedJoinRequestV2`, role/roster digest, pinned fingerprint, recipient install or signed ack. The V2 actor must authenticate before native CAS, and native CAS must re-check the signed/immutable mutation constraints against its *stored* snapshot. A JS-validated callback alone is race-prone.
2. **Idempotency**: V1's duplicate `epoch_commit(tx_id,group_id,digest,epoch)` returns false if those three stored strings match. It does **not** compare full prepared journal, exact new record/key identity/recipient receipts. The caller supplies `digest` without native recomputation. V2 must reject same ID/different authenticated contents and recover ambiguous after-commit status by reading durable journal and verifying complete digest.
3. **Key retirement**: V1 `commitEpoch` only inserts new sealed key; it does not atomically retire previous epoch key. Security v2 requires old key deletion/tombstoning in the same commit boundary. Even secure deletion cannot erase a secret previously copied by a compromised/revoked member.
4. **Epoch range**: V2 accepts epochs up to `0xffffffff` (4,294,967,295). Kotlin uses `maxEpoch=2147483647`, `Int`, and `epochHigh(): Int`. Native must use validated unsigned decimal/string or bounded 64-bit representation and reject overflow; do not truncate/wrap.
5. **Native error taxonomy**: Kotlin `execute` maps most failures to `SECURITY_UNAVAILABLE`. V2 needs stable distinguishable `CONFLICT`, `STALE_EPOCH`, `CORRUPT_STATE`, `REPLAY`, `KEY_MISSING`, `NOT_INSTALLED` and uncertain-result/retry semantics, with no sensitive payloads in logs.
6. **Transaction boundaries**: Android SQLite FULL commits can atomically update rows *in one database* under normal process crash and durable storage assumptions. They cannot atomically update an independently anchored high-water device counter, Keystore alias lifecycle, remote phone state or LoRa deliveries. An "after native success / before JS receives Promise" crash must be resolved through an immutable transaction receipt.
7. **Trust lifecycle**: Native V1 peer trust/metadata writes use separate sealed `meta` entries. V2 must bind role/owner/identity rotation and delegation state to the same authority CAS and detect stale peer fingerprint pins. Group leader and MeshCore channel PSK are neither owner genesis nor admin permission.
8. **A V2 group is not a V1 group**: V2 snapshots/key paths must be namespaced, versioned and migration-gated; do not invoke `SecurityMetadataStore.setGroup` or let V1 `GroupKeyManager` interpret a V2 snapshot.

### SQLite crash atomicity != hardware rollback resistance

The Android database is held in `noBackupFilesDir`, with `android:allowBackup=false`, and `PRAGMA synchronous=FULL`. Those measures help durability/backup hygiene. `nonce.high`, `epoch_high`, `epoch_commit` and sealed entries are all **in that same SQLite file**. Restoring the whole file to an older valid encrypted image can restore *both* the epoch and its supposed high watermark. AES-GCM protects authenticity of individual sealed values, not their freshness across historical backups. A retained Android Keystore wrapping key may still decrypt old database ciphertext.

Require an independent monotonic anchor with documented hardware/device evidence **or** a formally reviewed fail-closed rekey/re-anchoring ceremony that refuses any restored old epoch/key. If independent state is absent or inconsistent, never proceed from a reconstructed high watermark. Complete coordinated rollback remains an explicit threat until a proven external anchor exists.

V1 symmetric secret bytes necessarily transit React Native JS in base64; AES-GCM Keystore wrapping is **protection at rest**, not evidence that symmetric epoch keys are hardware non-exportable. V1 asymmetric private-key handles have the correct opaque model but exact Ed25519/X25519 hardware support is probe-gated and physically unverified at the reviewed SHA.

## Proposed additive Android-native V2 transaction boundary

**Do not re-use `AndroidSecurityEpochStorage` as `SecurityV2TransactionalStore`.** Android worker may add a version-2 table namespace or dedicated database with independent genesis pin, immutable canonical signed-preimage digests, prepared/committed/superseded transaction records, full roster snapshots, sealed epoch keys, recipient installed envelopes, issued distributions and authenticated acknowledgement receipts.

All proposed native calls should return a typed durable outcome: `committed`, `already-committed-identical`, `conflict`, `stale`, `unknown-verify-journal` or a stable non-secret failure code. A transaction whose Promise was lost must be recoverable by re-reading that transaction's canonical digest. A DB transaction must provide full CAS for expected epoch, exact roster digest, unchanged authority sequence and member fingerprint binding. All native methods should validate the complete versioned schema and reject extra fields, weak/short keys, negative/overflow epoch, non-canonical digests and malformed identity records.

**Suggested future adapter** (NOT implemented while native invariants are missing): `AndroidSecurityV2TransactionalStore implements SecurityV2TransactionalStore`, using only the new `ProposedAndroidSecurityV2NativeBridge`. Before first use, independently validate capability/schema, Keystore custody, group/journal recovery and epoch-fence integrity; obtain reviewed physical-device evidence. Each TS method must invoke exactly one corresponding atomic native operation and verify the returned typed transaction receipt against the expected digest. Treat network/storage failure as ambiguous until a read-only native recovery read verifies the journal; never treat `Promise<boolean>` or a fresh `setSecret` followed by `setGroup` as a commit. No implicit conversion of frozen V1 structures and no partial adapter that implements only some methods. A synthetically full mock surface **is not** production approval; the test-only inspector deliberately never authorizes activation.

Storage/provider tests required from Android worker: CAS under concurrent owners/processes; interrupted SQLite transaction before/after durable commit; app process death during bridge response; device reboot, key alias lost/revoked; corrupted AAD/ciphertext; coordinated backup restore; broken external fence; stale prepared journal; idempotent replay with altered digest; role-revocation race; hard key deletion and signed ack durability; lost recipient install before ack; Android API/firmware KeyInfo reports on Galaxy S22+ and other target devices. Device/emulator-specific evidence must distinguish skipped unsupported Curve25519 tests from passing hardware tests.

## Formal security issues beyond native storage

| Topic | Current evidence and residual risk | Approval gate |
|---|---|---|
| Owner genesis ceremony | V2 signs genesis and checks `PinnedOwnerAnchorV2`; test store lets caller pin. No real out-of-band owner-verification ceremony, secure native pin persistence, authenticated ownership transfer or compromised-owner recovery | Independent person/device confirmation, signed/pinned genesis, rotation/recovery policy and negative clone tests |
| Fingerprint ↔ Protocol node ID | V1 `DirectSessionManager` authenticates peer fingerprint, while Protocol v1 immutable AAD signs numeric `sourceNodeId`/`destinationNodeId`. No independently verified persistent mapping of node ID to identity/fingerprint was approved in V2 | Canonical identity/node-ID binding, conflict rejection, route-node reallocation/rotation rules, cross-device AAD vectors |
| Competing approvals | Test store CAS serializes competing transactions in one process. Android V1 `commitEpoch` CAS has no prepared digest/authority sequence; malicious simultaneous admins or two writers can fork logical group state | Multi-process DB serializability, signed total authority order or explicit conflict/reconciliation policy |
| Global convergence | Owner may locally commit and sign a distribution while receivers are disconnected. There is no distributed agreement that all members have the new key or current roster; V2 direct session transport cannot force delivery | Per-peer durable queue/resync receipts, snapshot/epoch convergence proof, explicit unresolved members |
| Recipient authorization | Recipient install proves local key possession and produces a signed ack, but V2's verified-ack ledger is stored on the **sender**. Recipient `resolveCurrentMembership()` cannot infer sender verified the ack, and there is no signed receipt-of-ack confirmation propagated back | Signed owner-issued installation confirmation/current authority checkpoint and local durable receipt + revalidation; remain unauthorized until verified |
| Admin delegation | V2 permits owner-signed, currently active admin preparation/commit. Current recipient install requires **owner-signed** distribution; an admin-only commit cannot be completed through this path. Admin->admin delegation and stale revocation synchronization are deliberately rejected | Separate reviewed owner co-signature/checkpoint or an authenticated current admin authority log before remote installation |
| Fresh epoch secrecy | V2 test store generates fresh 32-byte key, retires old local key, but Android V1 `commitEpoch` retains old key, and a compromised old member may have cached it | Atomic key retirement, rekey distribution, forward secrecy limitations and compromise response documented |
| Revoked stale key | Removed peer can retain old epoch key and read previously captured old traffic. Current V2 only has local epoch invalidation and role-credential revocation; complete member-removal rekey and offline revocation propagation are absent | Signed remove/rotate/notify/receipt transaction and staleness gate on each device |
| Protocol v1 AAD | Security v2 hashes immutable Protocol v1 `authenticatedHeader` and V1 AEAD binds bytes; different original header/node selector must fail. Transaction/credential/roster fields not in frozen header are signed inside V2 transcript | Cross-device byte-for-byte AAD and packet semantic/type ID review; no mutable hop info added |
| Fragmentation/loss | Current V2 distribution embeds a full signed snapshot, approval, join and V1 ciphertext; may exceed radio MTU. Transport has not assigned a reviewed Security v2 control subtype/fragmentation policy | Bound sizes, replay/duplicate-fragment rules, packet ordering, retransmit and incomplete-message timeout tests in protocol branch |
| Ack authenticity | Ed25519 ack is checked against current trusted recipient identity, issued distribution digest and current epoch; transmission callback is not a receipt | Durable signed ack journal, re-sign after crash, owner-verified confirmation, old-key/revoked-peer ack rejection and convergence tests |
| Restart/rollback | Deterministic fake models crashes/rollback. Android V1 epoch CAS is SQLite only and no V2 prepared/install journal exists | Native device power-loss/restart consistency, independent rollback anchor or reviewed fresh-key recovery |
| Downgrade | V2 objects carry version 2; V1 session transports the encrypted payload using negotiated Protocol v1 AAD. V2 control-subtype negotiation and "no V1 fallback after V2" policy are not yet approved | Explicit capability/feature negotiation, version pin per group/member, downgrade/replay vectors |

### Required cross-branch integration sequence (not performed)

1. Android worker reviews this document and `ProposedAndroidSecurityV2NativeBridge`. Implement **new** atomic V2 storage APIs and native tests on `feature/android-production-security-v1`, preserving its V1 interface and the live app gate.
2. Security v2 worker reviews native guarantees and receipts against all 15 `SecurityV2TransactionalStore` operations. Only **after** successful native tests, implement an explicit strict adapter to the versioned native bridge on the Security v2 branch; never cast V1 `epochStorage`.
3. Agree on independent genesis-pin provisioning, owner/admin sequence/role-revocation semantics, identity rotations and revoked member rekey before accepting remote epochs.
4. Protocol runtime worker defines the Security v2 control subtype, canonical node-ID↔fingerprint identity binding, immutable AAD conformance, bounded fragmentation, replay-safe retries and recipient receipt propagation. No new runtime is created here.
5. Run a physically tested multi-Android-device matrix covering real Keystore primitives, reboot/reinstall, interrupted commits, partitions, concurrent admins, stale replay, revoked peers, lost receipts, key unavailability and hardware/persistence rollback; inspect actual signed ledger/recovery results.
6. Independent formal Security v2 design and implementation approval, platform and supply-chain audit, explicit product consent/activation decision **on a separate authorized integration change**. Until that gate, the current compatibility code and `SecurityV2GroupTransactions` are non-production test/review only.

## Acceptance / release classification

- **Implemented and reviewable:** V2 domain-separated signed operations, fake transaction core, compile-time exhaustive Android operation matrix, passive fail-closed native-surface inspector and negative compatibility tests.
- **Simulated:** CAS, journal, power-loss and disconnected-member delivery using deterministic test providers.
- **Android present but insufficient:** Keystore-wrapped SQLite V1 metadata/key persistence, local SQLite epoch CAS and signed-unrelated V1 group record.
- **Missing/blocked:** Every proposed Android V2 method; atomic V2 roster/receipt/genesis/role lifecycle, hardware rollback evidence, actual physical provider tests, signed convergence/owner confirmations, verified identity/node-ID mapping, member-removal rekey and authorized protocol transport.
- **Production / multi-device activation ready:** **NONE.** All activation guards stay unchanged; passing Jest/Android compilation is not formal security approval.
