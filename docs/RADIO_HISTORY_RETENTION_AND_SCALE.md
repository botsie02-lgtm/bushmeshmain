# Local history retention and scalability review

The current native history uses one AES-GCM authenticated SharedPreferences value and a serialized JS write chain. The entire JSON snapshot is validated, encoded, encrypted and committed for each durable insertion; ordinary React state changes may queue an additional snapshot write. Startup decrypts/parses the whole store. Chat preferences are separately encrypted, with a native 1,000,000-character limit; large read-ID sets can exceed that limit. UI pagination limits rendering, not disk or JS history size.

The host regression benchmark runs 1k/10k/50k real snapshot rows, initial encoding, decode/restore, incremental snapshot encoding, scoped search/pagination, truncated JSON rejection and heap delta. These are host-only timings and approximate heap samples, not Android native commit latency, process RSS or cold start. The isolated Android instrumentation uses a distinct scratch preferences file and Keystore alias to measure 1k/10k/50k representative outgoing snapshots, actual native save/load/rewrite and Java heap/PSS samples. It also checks malformed-envelope recovery. This is not a true cold launch or peak-memory measurement. Physical device profiling is still required before setting supported capacity. No automatic history eviction or database migration.

Local clear uses exact persisted radio/configuration incarnation/slot/name. Pending outgoing journals block clearing. The existing serialized write chain commits remaining records and encrypted ID/replay ledger in one snapshot before updating UI. Exact replay IDs are excluded at restore and insertion; a later local association with equal scope/firmware timestamp/text is not proof of duplicate, so it is preserved separately with an explicit possible-replay label. Other scopes and ambiguous historical records are untouched. Read/star/pin cleanup is a separate serialized preference write after history commit; if cleanup fails, orphan IDs have no visible message and a warning is displayed. A second authenticated native marker, using a different AAD and atomically committed with the snapshot, rejects legacy unmarked saves and a missing or regressed ledger when the marker survives. Native load rejects single-snapshot rollback against the retained marker. Explicit full-storage reset removes both; whole-file rollback is still outside this protection. No channel writes, no remote deletion. Firmware lacks a unique persistent packet ID, so a legitimately equal post-clear occurrence may be separated. A replay under another incarnation cannot be proven to belong to the deleted conversation. This is not forensic erasure, anti-rollback, or protection against restoring an entire old app-data backup. Do not downgrade to a binary that does not preserve the optional retention ledger after clearing history.

## Future storage contract (not activated)

A versioned authenticated per-record journal and indexed metadata store should replace whole-history rewrites only after independently validating: stable record IDs and explicit local provenance; encryption at rest with platform key lifecycle and authenticated record/index binding; atomic commit of record, tombstone and relevant read metadata; durable receipt before acknowledgement; monotonic committed generation with rollback detection; bounded page queries and search without plaintext indexing outside protected storage; failure-safe recovery from interrupted journal append/checkpoint; non-destructive migration that reads/validates the original snapshot, imports into a shadow store, verifies counts/IDs/digests/retention, atomically activates after validation, and preserves the original until explicit successful recovery verification. A failed migration must continue reading the original store and must not overwrite it. Evaluate encrypted SQLite/SQLCipher licensing/build/maintenance and native key wrapping against Android 16 before dependency selection. No Security v2/W1 activation.

## Memory incident and bounded v1 repair

Failed Android API 36 instrumentation job 139720503177: 64,475,536-byte allocation at Base64.encodeToString, incremental write line 101; heap growth limit 201,326,592 bytes. The ASCII fixture computes to 24,177,820 bytes at 50k and 24,178,304 at 50,001 (32,237,760 Base64 characters plus implementation overhead), matching the observed failure. Smaller cases' logcat metrics were not collected after the failed run. The original benchmark retained the previous full plaintext during generation and saving of the next. The corrected fixture keeps only a digest/size/time between operations, uses pre-sized generation, isolated scratch preferences/keys, and verifies readback after every successful write. 50k initial and 50,001 update candidates must explicitly reject at the real native admission boundary, leave prior committed data unchanged, and report not committed rather than fabricate restore times. Retention-bearing rejection also tested.

The v1 message envelope (AES-GCM, same alias, AAD, Base64 and layout) is preserved. Native encryption now converts bounded UTF-8 chunks, writes cipher output through Base64OutputStream into one pre-sized byte buffer and constructs one final envelope String. JavaScript preflights per-row UTF-8 JSON size before full serialization; skips redundant writes of already committed state. Native still holds the complete JSON and final envelope, and SharedPreferences may retain/copy the old envelope and allocate during XML writing. Provider internals may buffer. Legacy restoration remains whole-snapshot; the guard checks available heap before decrypt/bridge, not before SharedPreferences XML parsing. No guarantee of bounded JS heap or recovery of an arbitrarily huge legacy file. No new key/format or database migration.

Admission is non-destructive: total serialized snapshot plus separate retention argument at most 16 MiB and at most heap/12, with 32 MiB reserve and an additional 8x candidate-byte headroom estimate. Restore uses 4x encoded-envelope headroom plus reserve without the fixed new-write cap, allowing legacy reads where safe. These conservative estimates derive from the observed allocation amplification and concurrent RN runtime; not measured universal safe limits. Dynamic headroom can reject smaller snapshots; the byte threshold is not a supported message count. No automatic eviction, compaction, reset or heap increase. Failed capacity admission never edits preferences. On disk commit failure the in-memory SharedPreferences values are restored with a synchronous rollback; an unconfirmed rollback fences subsequent native writes until restart. Disk failure cannot guarantee restoration if rollback itself fails. Inbound consumer retains and retries failed persistence rather than acknowledging; its existing finite queue cannot guarantee indefinite lossless reception when full. Existing restored history remains exportable/clearable when a new save fails. A deliberate local clear can reduce history but its ledger also consumes capacity. Full indexed/journal storage remains necessary for much larger history and requires the migration evidence already specified above.
