# Native invitation QR dependency review

Pinned ZXing core 3.5.4 and JourneyApps Android embedded 4.3.0, Apache-2.0. References: https://github.com/zxing/zxing/releases and https://github.com/journeyapps/zxing-android-embedded/releases, https://github.com/journeyapps/zxing-android-embedded. Core is maintained separately; embedded 4.3.0 has a slow release cadence and uses the legacy Android camera API. This is a bounded Android-native integration, not a React Native camera framework or a guarantee of Android 16 camera compatibility. CI compilation and actual hardware scanner acceptance are required. No network scanning or image upload, no gallery or storage permission, camera optional and requested only on explicit scan. Existing invitation decoder validates the payload; existing provisioning verifies duplicate name/key, full capacity and radio identity before writing. Secure native dialogs have no stored QR bitmap and are dismissed on host pause/destroy, timeout or cancellation. QR display itself is explicit sharing; no screenshot or file export. Manual paste remains available. No new native ownership or background service.

Additional review: upstream embedded 4.3.0 was released 25 October 2021; slow maintenance is a material risk. Public upstream/advisory searches did not establish a direct advisory against these exact runtime coordinates, but this is not a resolved transitive dependency/SBOM vulnerability audit or assurance of safety. Restrict the decoder to QR, bound the accepted payload to 512 characters, validate every payload using the existing contract, never open scanned URLs, and use explicit provisioning confirmation. Camera permission is optional, denied access retains manual fallback. Android 16 physical scanner/torch testing remains mandatory before acceptance.
